## Architecture review and cleanup — 2026-11-13

The user asked for "a comprehensive architectural review & cleanup: focused on organization, modularity and maintainability. Code duplication and dead code may be an issue too", asking what a top Rust architect would complain about, with DDD "where it makes sense". First a review and a plan; shown both, the user answered: "I trust you decide the best way, so I go with your recommendations on all". The rules are [ADR-020](DECISIONS.md#adr-020--code-architecture-layers-bounded-contexts-and-lints-2026-11-13).

**The review** (read-only; Clippy with the pedantic and nursery groups in a scratch target folder, a scan for repeated blocks, and four reviewers reading domain, infrastructure, `app/src/window` and the rest of the app). Good: one-way crate dependencies, a `SAFETY:` comment on every `unsafe` block, no TODOs in code, no document text in logs, no blocking I/O on the GTK thread, weak references in signal closures. The complaints, most serious first:
1. The window is a god object: `Inner` has 43 fields and 27 files add methods to `Window`; feature state is grouped by milestone (Replace in Files in `Nav`, the word count in `ToolState`); actions are matched twice and the inner matches end in `_ => {}`.
2. `domain/src/actions.rs` (2,926 lines) names each action three times (the enum, a hand-kept `ALL` of 209, a 1,184-line `spec()`) and also holds menus, accelerator parsing and keyboard-layout tables.
3. Facts defined several times: the decode report's fields in five structs copied field by field; the NUL placeholder and the bulk-edit threshold in two crates; atomic writes five times with different durability; two number sequences, two fuzzy matchers, two untitled counters, two highlight-limit functions.
4. GTK and file formats in the domain (style-scheme XML, libadwaita CSS, `session.json`, the TOML parsing) while GTK-free logic sits in the app (`updates::answer`, `count_words`, the banner decisions, `edits::Marks::map`, `loader.rs`).
5. Primitive types where mixing is a bug risk: character and byte offsets both `usize`, tab ids as `String`, `view: u8`, tab width `u32` here and `usize` there; about 640 lossy `as` casts in the app.
6. Settings keyed by strings, each written in four places, with an `unreachable!` setter.
7. Stale-result handling written by hand about 20 times; six loops polling for a page to load; a new OS thread per worker job.
8. Find in Files and Replace in Files nearly duplicated in infrastructure and in the window.
9. The 6,700-line self-test harness in the release binary, with about 60 public functions only it uses and about 50 direct reads of `window.inner`.
10. About 50 public items used only by tests; no `#[must_use]`; two import paths for some items.
11. No `[workspace.lints]`, no CI outside the developer's machine, and the M0 spikes (8,300 lines) built on every run.
12. A confusing layout (`search.rs`, `page_search.rs` and `window/find.rs`; `marks.rs`, `window/marking.rs` and `edits::Marks`), and about 280 milestone tags in comments.

**Found along the way:** restoring a tab from its backup decides highlighting with the built-in limits (`view::highlight_by_default`, `app/src/window/session.rs:641`), while opening a file uses `config.toml`'s (`Settings::highlight_by_default`); and `worker::pending()` stays raised when a waiting job's future is dropped.

**The decisions** (the agent's recommendations, accepted as a whole):
- All six phases below, in order, each step a commit on the branch `cleanup/architecture` that passes `bash tools/ci.sh --ui`; `main` takes the branch when the whole cleanup passes, and is pushed then.
- The self-test harness becomes the default-on Cargo feature `selftest`; the Arch package and the Flatpak are built without it.
- The spikes leave the tree; the tag `m0-spikes` keeps them in history.
- Behaviour may change only here: the command palette, the language picker and the encoding picker rank with quick open's fuzzy matcher, and number sequences (Insert Numbers, the column editor) share one overflow rule.
- PLAN.md's dated history before 1.0 moves to `docs/history/`; CONTRIBUTING.md becomes the outside contributor's guide; comments lose their milestone tags.
- CI on GitHub Actions in an Arch Linux container (the GTK, libadwaita and GtkSourceView versions Stet needs), pushed with `main`.
- No version bump or release is part of this; the highlighting fix waits for the next release.

**The plan:**
- **Phase 0 — the safety net.** The 16 self-test scripts that stopped on GTK 4.24's Broadway abort cover column mode, the text tools, settings, the session, focus, the context menu and large files, the areas the cleanup touches most. Land `tools/headless.sh`'s use of Sealwax's patched daemon (the user's choice of 2026-11-13, until then uncommitted) and confirm every script runs.
- **Phase 1 — quick fixes and hygiene.** The two bugs; `[workspace.lints]`; dead code removed and the rest narrowed to crate-private; one home for each duplicated constant and rule; `crossbeam-channel` dropped; logging set up in the app; one `DecodeReport` in place of the decode facts copied through four structs; the spikes removed; milestone tags out of comments.
- **Phase 2 — pure logic moves down,** with tests: to the domain the update answer, word count, home expansion, banner decisions, offset mapping, search-hit lines; to infrastructure the loader, the theme's file I/O and the session store's retry; out of the domain the GTK writers (to the app). The persisted formats stay with their models ([ADR-020 amendment](DECISIONS.md#adr-020-amendment--formats-stay-with-their-models-2026-11-13)).
- **Phase 3 — the domain.** The action registry generated from one table and split into registry, menus and keys; settings declared once per setting; value objects; modules regrouped by bounded context.
- **Phase 4 — infrastructure.** One durable-write module; one job and walk module under Find in Files, Replace in Files and the project walk; `thiserror` errors without strings.
- **Phase 5 — the app.** A probe module for the self-tests; a job runner on GLib's thread pool with stale-result tokens, a debouncer and `page.loaded()`; one streaming run for Find and Replace in Files; feature components that own their state and actions; a `FindBar` that hides its widgets; `editor.rs` split and `DocState` reshaped; the window as a GTK subclass.
- **Phase 6 — the open-source finish.** The `selftest` feature and the packaging; `docs/ARCHITECTURE.md`; the history split; CONTRIBUTING; the CI workflow.

## Execution model

Stet is delivered in explicit milestones. Sizes are focused engineering days.

Rules:

- keep the application runnable after each meaningful slice;
- keep work in progress small;
- every milestone ends with a **preview gate**: screenshots in `tools/progress/`, a dated entry in this file, and the user's approval;
- record decisions with long-term cost as ADRs in [DECISIONS.md](DECISIONS.md);
- every `git init`, commit, push, package build or install needs a dated user authorization in the log below before it happens;
- never invent acceptance evidence; record what was run, when, and its caveats;
- record follow-ups in this file instead of hiding TODOs in code;
- do not expand 1.0 scope because an idea is interesting (see Scope control).

## Scope control

Do not implement before Stet 1.0. Add ideas to these lists instead of the code.

**1.x (after 1.0):**

- code folding, macros, multi-caret, Run (F5), tail -f mode;
- word completion, auto-close pairs;
- a save-as-administrator helper using pkexec;
- a Preferences GUI and keymap editor, and a VS Code-style preset;
- the full character-sets menu and OEM code pages;
- document list and folder workspace, print, `recent.json`, and an omarchy-shell plugin.

**Later:**

- function list and structural folding (tree-sitter);
- importing user-defined language (UDL) files (user `.lang` files work from day one);
- spell check;
- hex view;
- JSON tree view.

**Never:**

- plugin ABI or scripting;
- a Style Configurator (the theme drives colours);
- an FTP plugin, an auto-updater, always-on-top (not possible on Wayland), clipboard history;
- Markdown preview (Omawrite covers it), i18n for 1.0, named session files.

Moving an item between tiers is a user decision, recorded as a dated entry here and an amendment to [ADR-013](DECISIONS.md).

The repository is the only project memory; there is no external tracker to mirror.

This file contains:

- the current status and active milestone;
- blockers and follow-ups;
- the authorization log;
- dated entries for progress and preview gates, newest first;
- scope control.
