> Recorded on 2026-09-30 under the working name Notes. Since [ADR-010](../DECISIONS.md#adr-010-accepted--stet-2026-09-30) the crate `notes-spikes` (Rust path `notes_spikes`) is `stet-spikes` (`stet_spikes`), and the `NOTES_*` environment variables are `STET_*`. The raw JSON lines under `.local/`, the generated tables under `target/spikes/s2/` and the fixture `target/fixtures/search-1m.log` were deleted on 2026-09-30 to free disk space; regenerate the fixture with `python3 tools/gen-fixtures.py` and re-run the spike to regenerate the output. Milestone: M0. Run: 2026-09-30, headless (GTK Broadway). Binary: `spikes/src/bin/s2_search.rs`.

**Overall:** GtkSourceView is fine for find, count, highlight and Find Next, with a pattern-translation layer. It is **not** fit for large Replace All: `replace_all` is too slow on 1M matches, and it blocks the GTK thread. Undoing its result with the view attached costs about 0.1 ms and 8.5–8.7 KiB per replacement. Its template dialect also differs from Boost-style templates in ways that cannot all be translated. Replace All should use our own PCRE2 matching and template expansion on a snapshot, applied as a bulk edit (ADR-003). This is a design correction inside the GTK stack, not a toolkit no-go.

## Purpose

Check, before M1, that GtkSourceView's `SearchContext`/`SearchSettings` can carry the plan's search features (ADR-005):
- the cost of counting every occurrence in a 1M-line file, with highlighting on and off;
- `replace_all` with a capture group and case conversion: its speed, whether it is one undo step, and its count;
- which replacement syntax GtkSourceView accepts;
- which PCRE2 features work through the widget, including multi-line patterns and Boost's `\<` `\>`.

## Method

The binary loads `target/fixtures/search-1m.log` into a `sourceview5::Buffer` inside an irreversible action, so the undo history starts empty. It shows the buffer in a realized `View` (1000×700 window, inside a `ScrolledWindow`) and waits for 2 frames. It then waits until a `G_PRIORITY_LOW` idle callback runs, which means the view's idle line validation has drained. The fixture was generated by `tools/gen-fixtures.py`: 149,192,114 bytes, 1,000,000 lines, ASCII, one match per line for every pattern used.

- **Count.** A new `SearchContext` is created with no search text, and the main loop is drained. The clock starts when `set_search_text` is called and stops when `occurrences-count` stops being −1. The loop is driven by `notes_spikes::run_main_loop_until`. After each run the spike waits for one frame, then disposes the context and times that too.
- **Replace all.** The spike calls the C function `gtk_source_search_context_replace_all` directly (see [binding defects](#binding-defects)) and times the synchronous call. The resulting text is compared for **exact string equality** with an output computed independently in Rust (the transform is unit-tested), and the returned count is compared with the expected count. "Count available again" is the time until `occurrences-count` is known after the replace.
- **Undo.** The spike calls `buffer.undo()` once and times it. It then checks three things: the text equals the original exactly (a 64-bit SipHash digest is also recorded); `can_undo()` is false; and `can_redo()` is true. On the first run of each set it also calls `redo()`, checks the result equals the expected text, and undoes again; `--no-redo` skips this step (sets B and the diagnostics). Before undoing, the spike drains the main loop and puts the editor into one of these states:
  - `live`: the search context stays alive and highlighting;
  - `cleared`: the search text is set to None;
  - `dropped`: the context is disposed. This is the realistic state;
  - `nobrackets`: `dropped`, plus `highlight-matching-brackets` off;
  - `noprimary`: `dropped`, plus the buffer removed from the PRIMARY selection clipboard;
  - `detached`: `dropped`, plus the view switched to an empty buffer.
- **Bulk path.** Inside one user action, delete the whole text and insert the precomputed dense result, then undo.
- **Probes.** For each probe, a fresh small buffer is created. The spike waits for the scan, reads `occurrences-count`, and collects matches with `forward()` from the start (or from a given offset), stepping over empty matches. Template probes call `replace_all` on a fresh buffer and record the text or the `GError`.
- **Watchdogs.** Every step that can block has a deadline: 10–600 s per step, checked by a watchdog thread that prints `timeout` and exits. The same thread caps RSS at 16 GiB. `run_main_loop_until` also fails on timeout. `tools/headless.sh` bounds each process (`NOTES_HEADLESS_TIMEOUT`). No step hit a deadline or the cap.

Commands, run from the project root. Raw JSON lines are in `.local/s2-*.jsonl`, and the generated tables in `target/spikes/s2/`.

```sh

# probes (pattern features, templates, bindings)
NOTES_HEADLESS_TIMEOUT=300 tools/headless.sh 12 cargo run -q --release -p notes-spikes --bin s2_search -- --probes-only
# A: counts, replace-all with undo in the detached state, and the bulk path, 3 runs each, 1M lines
NOTES_HEADLESS_TIMEOUT=3600 tools/headless.sh 12 cargo run -q --release -p notes-spikes --bin s2_search -- --perf-only --runs=3 --undo=detached --tag=1m-a
# B1–B3: dense replace-all in a fresh process, undone with the view attached (run 3 times; redo skipped to bound memory)
NOTES_HEADLESS_TIMEOUT=3600 tools/headless.sh 12 cargo run -q --release -p notes-spikes --bin s2_search -- --replace-only --cases=dense --runs=1 --undo=dropped --no-redo --tag=1m-b1

NOTES_HEADLESS_TIMEOUT=3600 tools/headless.sh 12 cargo run -q --release -p notes-spikes --bin s2_search -- --replace-only --cases=sparse --runs=3 --undo=dropped --tag=1m-c

NOTES_HEADLESS_TIMEOUT=1800 tools/headless.sh 12 cargo run -q --release -p notes-spikes --bin s2_search -- --replace-only --cases=dense --lines=100000 --runs=3 --undo=<live|cleared|dropped|nobrackets|noprimary|detached> --no-redo --tag=100k-<state>
NOTES_HEADLESS_TIMEOUT=1800 tools/headless.sh 12 cargo run -q --release -p notes-spikes --bin s2_search -- --replace-only --cases=dense --lines=200000 --runs=3 --undo=<dropped|detached> --no-redo --tag=200k-<state>

rg --pcre2 -o '<pattern>' target/fixtures/search-1m.log | wc -l
```

## Results

### Loading (context for everything below; not an S2 bar)

Over 5 processes, `set_text` of 149 MB took **965 ms** median (949–981). The first 2 frames came 1.14 s later (1.06–1.81). The view's idle line validation then kept the main loop busy for another **51.8 s** (51.3–52.5) before a low-priority idle ran. RSS went from 216 to 516 MiB. S1 owns these numbers. S2 is affected because search scans and rescans run as idle work behind this validation.

`max-undo-levels` on a new `GtkSourceBuffer` read **200**. It is not 0 (unlimited), as ADR-003's reasoning assumed.

- **Correctness.** Every count equals `rg --pcre2 -o … | wc -l` (and `rg -F` for the literal) and Python `re` on the same file. The counts agreed across all three runs.
- **Highlighting** costs 1.1–1.8× extra, even though tags are applied either way.

- **Disposing a context** that highlighted 1M matches blocks for about 0.5 s (removing the tag).

- **Where the cost is.** With the view attached, undo costs about 105–121 µs and 8.5–8.7 KiB of RSS per replacement. It is linear: 10.5 s at 100k, 22.3 s at 200k, 121 s at 1M. The cost is on the view side:
  - the search context's state makes no difference;
  - neither do bracket matching or the PRIMARY clipboard;
  - with the buffer detached from the view, undo is 6–7× faster and RSS barely moves.

  The likely cause is that GtkTextHistory moves the selection for every sub-action, and GtkTextView reacts to each move. The root cause was **not** isolated.
- **Memory.** The extra RSS is reused by later undo passes in the same process rather than growing further. At 1M replacements, though, one undo needs about 8.2 GiB.
- **Undo levels.** A single history step can hold 1M edits whatever the `max-undo-levels` value.

### Replacement template syntax (determined empirically)

GtkSourceView parses the replacement with GLib's grammar: the errors are GLib's `Error while parsing replacement text …`. One rule is not documented: **escapes are only processed when the template contains at least one group reference.** A template without a reference is validated, then inserted verbatim. Evidence:
- `<\n>` inserts a backslash and `n`, but `<\1\n>` inserts a newline;
- `<\\>` inserts two backslashes, but `<\1\\>` inserts one;
- `<\x41>` stays literal, but `<\1\x41>` gives `A`;
- `<\Uab\E>` stays literal.

| Syntax | Result | Users of Boost-style templates need |
|---|---|---|
| `\0`, `\1`…`\99` (`\10` = group 10), `\g<n>`, `\g<name>`, `\g<1>0` | work; a missing group (`\2`) gives an empty string | yes (`\1`, `\0`) |
| `\U` `\L` `\E` `\u` `\l` | work when a reference is present; `\U\1` without `\E` also works. Unicode-aware (`café` → `CAFÉ`) | yes |
| `$1`, `${1}`, `$0`, `$&`, `$+{name}`, `$10` | **inserted literally** | yes, all of them |
| `\U$1\E` (the plan's wording) | inserted literally (it has no reference in GLib's grammar) | yes |
| `\n` `\t` `\r` `\v` `\f` `\a` `\b` `\\` `\xHH` `\x{HHHH}` | processed only if a reference is present; otherwise inserted as typed | yes (`\n`, `\t`, `\\`) |
| `\q`, `\e`, `\>` (unknown escapes) | error `unknown escape sequence`; a trailing `\` gives `stray final "\"` | — |
| A real newline character | inserted | — |
| Plain-text (non-regex) mode | the template is inserted verbatim (`\U\0$1` stays as typed) | — |
| `gtk_source_utils_unescape_search_text` (candidate for Extended mode) | converts `\t` `\n` `\\`; leaves `\x41` and `☺` literal | Extended mode needs `\xHH` |

Some literal text cannot be expressed at all. Take a replacement whose literal text contains a backslash followed by a digit or `g`, and which has no real group reference. `\1` is parsed as a reference, while `\\1` has no reference and is inserted as two backslashes plus `1`. So the Boost-style dialect cannot be mapped onto this one mechanically in every case. With a real reference present, `\\` does give one backslash: `<\\\1>` → `<\alice>`.

### PCRE2 features through SearchContext

The full table (52 probes) is in the [appendix](#appendix-a-pattern-probes). Summary:

- **Supported and correct:**
  - lookbehind, including bounded variable-length (`(?<=\w{2,4}=)`, PCRE2 ≥ 10.43), lookbehind across a line break, and lookbehind that looks before the iter where Find Next starts;
  - negative lookbehind and lookahead;
  - `\R`, which matches LF, CRLF and a lone CR in the buffer;
  - named groups (`(?<n>)`, `(?P<n>)`) and backreferences (`\1`, `\k<n>`, `(?P=n)`);
  - multi-line patterns: `foo\nbar`, a real newline in plain-text search, three-line patterns, `\s` and `[^x]` across newlines, `(?s).`;
  - `^` and `$` per line, `$` before CRLF, `\A` and `\z` for the buffer;
  - case-insensitive search, including non-ASCII (`CAFÉ`/`café`), and inline `(?i)`;
  - Unicode-aware `\w`; `\b`, and `\b` and `^` seeing the character before the start iter;
  - `at-word-boundaries` for text and regex. It treats `user_x` as one word, as `\w` does;
  - possessive and atomic groups, `\p{Lu}`, `\x{263A}`, `\xhh`, `\t`, `\Q…\E`, `\h`, `\N`, recursion `(?R)`, `(?x)`;
  - PCRE2 compile errors reported with offsets through `regex-error` (`missing closing parenthesis: offset 9`, `unrecognized character follows \: offset 2`).
- **`\K`: partly broken.** The count (2) and highlighting (`[5,10)`, `[16,19)`) are right. But `forward()`, `backward()` and `occurrence_position()` find nothing, and `replace_all` replaces 0. Find Next and Replace cannot work with `\K`. Rewriting `X\KY` as `(?<=X)Y` works when X has bounded length.
- **Zero-length matches: ignored everywhere.** `^` and `$` count 0, `forward()` finds nothing, and `replace_all` replaces 0. `^(.*)$` → `> \1` skips empty lines (`"a⏎⏎c"` → `"> a⏎⏎> c"`). The common editor idiom "regex `^` → prefix every line" does not work through the widget.
- **Boost `\<` `\>`: unsupported, and silently wrong.** PCRE2 reads them as literal `<` and `>`, so `\<user\>` matches `"<user>"` with no error. The translation `\b(?=\w)` / `\b(?<=\w)` gives the Boost result.

### Binding defects

- **`sourceview5::SearchContext::replace_all` (0.11.2, `src/search_context.rs`).** It does `assert_eq!(is_ok == 0, !error.is_null())` on the C return value. That value is a `guint` *count*, not a boolean. The wrapper **panics when nothing matches** (measured: `assertion left == right failed`, with the C call returning 0), and it discards the count. The spike calls `sourceview5::ffi::gtk_source_search_context_replace_all` directly (`replace_all_counted`).
- **`SearchContext::replace`** has the same shape, but with `debug_assert_eq!`. By reading the code (not tested): in release builds, a range that is not a match returns `Ok(())` without replacing anything.

## Caveats

- **Broadway, not Wayland.** Broadway renders in software and no browser was connected. The costs measured here are CPU work on the GTK thread (buffer, layout, search, undo), not GPU painting, but the view-attached undo cost must be re-measured in the real app on Hyprland. Keystroke-to-paint latency on real Hyprland must be measured manually by the user (S1).
- **Other load.** Other spikes ran on the same machine at the same time. Most repeats agreed within a few percent (spreads are in every table), but absolute numbers may be a little high.
- **What the counts measure.** Counts were taken after the view's idle validation had drained. A search started right after opening a large file would first wait behind about 52 s of validation. That is inferred from the rescan timings, not measured directly.
- **The fixture.** It is ASCII with at most one match per line. Replace output was checked against a hand-written transform (unit-tested) plus counts from ripgrep and Python `re`; it was not checked against a second regex engine's full output.
- **Bulk-path estimate.** It combines the measured buffer swap (1.82 s) and undo (1.37 s) with ripgrep's PCRE2 10.45 as a stand-in for our matcher (0.30 s, no case conversion). Snapshot cost (`buffer.text()`) and mark remapping were not timed here; S1 measures snapshots.
- **RSS.** Figures are `VmRSS`/`VmHWM` of the process. glibc keeps freed memory, so RSS after an undo overstates live memory, but the peak is real demand.
- **Diagnostic runs** used 100k and 200k lines. The `live` state (context highlighting during undo) was not run at 1M, because the `dropped` state already costs 121 s and 8.2 GiB.
- **Earlier runs.** Exploratory single runs (n=1) at 100k lines found the undo problem. They are superseded by the n=3 tables above and are not cited, except for one number: a 100k dense redo with the view attached took 17.4 s.

## Recommendations for the plan

1. **Amend ADR-005.** Split in-document search:
   - **SearchContext** keeps highlight-all, the occurrence count ("counting…" while it is −1) and Find Next/Previous.
   - **Replace All** (and Replace All in all open documents) runs our own engine:
     1. take a snapshot;
     2. match with the `pcre2` crate (JIT) on a worker thread;
     3. expand Boost-style replacement templates in `domain::search::template` (`$1 ${n} $& $+{name} \1 \U \L \E`, `\n \t \\`);
     4. apply the result on the GTK thread per ADR-003.

   This fixes the 8 s freeze, the 121 s / 8.2 GiB undo, `$n` templates, zero-length matches, `\K`, and the binding panic in one move. Use the same engine for the single Replace button, so there is only one template dialect.
2. **Amend ADR-003.** Set the bulk threshold by **edit count**, not by document size. With the view attached, undo costs about 0.1 ms and 8.5–8.7 KiB per edit: 49,883 edits already take 4.3 s to undo. Suggested rules:
   - above about 2,000 edits, replace one span (first to last match) or a few large chunks inside one user action, and remap marks and bookmarks;
   - at 1M lines, a whole-text swap costs 1.8 s, and its undo 1.4 s;
   - correct ADR-003's "`max_undo_levels` defaults to 0": it read 200 here.
3. **Add a pattern-translation step before SearchContext** (`domain::search::translate`):
   - `\<` → `\b(?=\w)` and `\>` → `\b(?<=\w)` (verified);
   - `X\KY` → `(?<=X)Y` when X has bounded length; otherwise use our own engine for Find Next;
   - detect patterns that can match the empty string (`^`, `$`, `x*`). SearchContext ignores zero-length matches, so route those to our own engine for count and navigation, or tell the user.
4. **Wrap the FFI.** Never call `sourceview5::SearchContext::replace_all` or `replace` directly. If either is ever needed, wrap the FFI call as the spike's `replace_all_counted` does, and file an issue upstream (gtk-rs / sourceview5-rs) about the `guint` return.
5. **Keep our own Extended-mode unescape.** `utils_unescape_search_text` has no `\xHH`.
6. **Adjust the pass bars.**
   - Keep "Replace All over 1M lines ≤ 5 s", but measure it end to end through our path (snapshot, match, expand, apply). Add "GTK thread blocked ≤ 2 s", and "undo of that Replace All ≤ 2 s with RSS growth ≤ 2× the file size".
   - Rephrase "`\U$1` works" as "Boost-style templates `\U$1`, `${1}`, `$&`, `\1` work in Replace All".
   - Record the count at 1M lines (1–8 s of idle work) as informative, not as a bar.
7. **Large-file mode.** The plan's rule for 50–256 MB already turns highlight-all off, and that is worth keeping: highlighting adds 1.1–1.8× to the count, and disposing a context with 1M highlighted matches blocks for 0.5 s.
